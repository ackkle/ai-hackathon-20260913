# リザーブ・マシン 要件定義書 v0.3 — メンバーC案

- チーム：AIハッカソン・チーム15
- 作成日：2026年9月13日（v0.1）／更新：2026年9月13日（v0.3）
- 位置付け：個人案。チームの正式仕様ではない。
- v0.3での変更：**入出力をB案に揃えた。** 記録（Takeout zip・スクリーンタイムのスクショ）のアップロードを廃止し、入力は本人への質問、出力はカレンダー予定とする。これに伴い「願望を聞かない」という v0.1〜v0.2 の主張は取り下げる。

## 1. 一文で

曖昧な願いを受け取り、**10年後にそれを続けている生活**を、初期費用・月額・週何時間という**値札つき**で提示し、最初の1日をカレンダーに予約させるアプリ。

## 2. 背景・前提

- 10年後、稼ぐこと・働くことの多くをAIが代わりに行う
- 浮いた時間の使い方を、多くの人は決められない
- 週休3日制の導入企業では、この問題はすでに起きている

## 3. 本案の主張（v0.3での差分）

入出力をB案に揃えたため、本案の主張は次の2点に絞られる。

| 主張 | 内容 | B案との違い |
|---|---|---|
| 空白を先に見せる | 願いを聞く前に「あなたには年◯日の空白が来る」と提示する | B案は願いの入力から始まる |
| 10年後に値札をつける | 逆算の到達点を10年後に置き、初期費用・月額・週何時間で示す | B案の到達点は1年後・3年後。数字は貯蓄・積立が中心 |

**この2点以外はB案の設計をそのまま使う。** 逆算の階層・質問の作り方・カレンダー登録・完了記録・再計算は、B案に設計がある（第10章）。

## 4. ターゲット

### 4.1 定義

外から空白が降ってくる人。やる気がないのではなく、やる気を仕事に吸われていて、空白を感じたことがない。だから空白が来ることが少し怖い。

| 空白の降り方 | 具体像 | 位置づけ |
|---|---|---|
| AIが仕事を減らす | 30代エンジニア | v0.2までの主ペルソナ |
| 会社が週休3日にする | 増えた1日の使い方が分からない会社員 | 実現性の根拠 |
| 定年が来る | 10年後の60代＝今の50代 | 展開性 |
| 就活が終わる | やることのない大学生 | 展開性 |

### 4.2 ペルソナ依存が解消した

v0.2までは入力がGoogleテイクアウトだったため、**それを書き出せる人（エンジニア）にしか成立しない**という制約があった。v0.3で入力がテキストと選択肢になったことで、この制約は消えた。

A案の佐藤さん（48歳・事務職）でも、B案のけんたさん（32歳・事務職）でも、本案は成立する。**統合会議でペルソナを統一する際、本案は制約にならない。**

## 5. 提供価値

気づきではなく、**時間とお金を先に確保した未来が1つできること**。

## 6. 体験の流れ

1. **空白を見せる** — 願いを聞く前に、空白の量を提示する（週休3日なら年52日、10年で520日）
2. **願いを聞く** — 自由入力。曖昧でよい。「まだ分からない」も可（B案①と同じ）
3. **質問に答える** — 使える時間・費用・許容できる負担など（B案①と同じ）
4. **10年後に値札をつける** — AIが「10年後にそれを週◯日続けている生活」と、初期費用・月額・週何時間を提示する（**本案の中心**）
5. **予約する** — 値札つきの予約票を発券し、最初の1日をカレンダーに登録する
6. **伴走する** — 完了を記録し、次の一歩が再計算される（B案④と同じ）

資産をどう作るかは本人の仕事。本案は値札を出すまでで止める。

## 7. 入力（B案と同じ）

- 願いの自由入力（曖昧でよい。「まだ分からない」も可）
- AIが返す質問に選択肢中心で回答する。「分からない」を選べる
- 分からない項目は統計の中央値などで仮置きし、「仮」と明示する

記録（視聴履歴・スクリーンタイム・カレンダー）のアップロードは**行わない**。理由は第9章。

### 質問の中身に関する提案

入出力の形はB案と同じだが、**質問の中身を「何がしたいか」ではなく「最近やっていること」に寄せる**と、v0.1からの思想を形式を変えずに残せる。

例：「この半年で、頼まれてもいないのに時間を使ったことは？」（選択肢＋自由記述）

形式はB案の質問5問のままなので実装への影響はない。採用可否は統合会議で決める。

## 8. 出力（B案と同じ器＋値札）

出力先はB案と同じくカレンダー予定。ただし予約票の券面に**値札**を載せる。

| 券面項目 | 内容 | 出どころ |
|---|---|---|
| 予約番号 | 形式例。実装では重複を避ける | — |
| 10年後の生活 | 1行（例：週3日、◯◯をしている） | AIの推定 |
| 確保する空白 | 年◯日／年◯時間 | 制度からの計算 |
| 初期費用 | ◯円 | 統計の参照値またはAIの推定 |
| 月額 | ◯円 | 統計の参照値またはAIの推定 |
| 週の時間 | ◯時間 | 本人の回答 |
| 最初の1日 | 日時と、その日にやること | 本人の確定 |

**値札の各項目に出どころを表示する**（本人の回答／統計の参照値／AIの推定）。B案の設計をそのまま使う。出どころのない金額を券面に刷ると「その根拠は？」に答えられないため、ここは省略しない。

カレンダー予定の説明欄にも値札を書き込み、カレンダー側だけを見ても内容が分かるようにする（B案③と同じ）。

## 9. 記録の取り込みを取り下げた理由

v0.2では入力をGoogleテイクアウトのzipとスクリーンタイムのスクショにしていたが、次の理由で取り下げる。

- **審査員が公開URLで試せない。** テイクアウトを書き出していない審査員はアプリを体験できない。実現性（動くか・使えるか）で最も重い減点になる
- **ペルソナがエンジニアに固定される。** 統合会議でペルソナを統一する際の障害になる
- **前提が未検証だった。** 視聴履歴から「流入経路」を判別できるかが確認できておらず、できない場合は抽出結果が凡庸になる
- **「スクリーンタイム＝空白」は修辞。** 「それは空白ではなく使っている時間では」と返される

記録からの抽出は、展開性（第12章）に置く。

## 10. A案・B案との関係

v0.3で入出力をB案に揃えたため、**本案は独立した3案目ではなく、B案に対する2つの修正提案**になった。統合会議ではそのように扱う方が速い。

| 論点 | 採用する案 | 理由 |
|---|---|---|
| 入口の入力形式・質問 | B案 | v0.3で揃えた |
| 逆算の階層・数字の出どころ表示 | B案 | 設計済み。本案の値札にもそのまま使う |
| カレンダー登録・完了記録・再計算 | B案 | 設計済み |
| 保存・失敗時の動作・データ形式 | B案 | 設計済み |
| **逆算の到達点を10年後に置くか** | **C案** | お題（10年後の当たり前）に出力で直答できる |
| **値札（初期費用・月額・週何時間）** | **C案** | 「時間とお金を先に確保する」を成立させる |
| マインド面（気が重いときは／始める言葉） | A案 | 3案で最も丁寧。予約票の券面に足せる |

## 11. 統合会議で決めること

v0.2で挙げた「ペルソナの矛盾」は解消した（第4.2章）。残る論点は次の2つ。

### 11.1 逆算の到達点を10年後に置くか

B案は1年後・3年後、本案は10年後。**両方は置けない**（階層が深くなり、4時間では組めない）。

- 10年後に置く利点：お題に出力で直答できる。展開性の説明がしやすい
- 1年後に置く利点：数字の現実味が保てる。10年後の金額はAIの推定に寄りやすい

### 11.2 実装量の上限

B案の完成条件12項目に本案の値札を足す形になるので、B案単体より増える。

fableの採点では、B案の最大の減点要因は**Google OAuthを本命に置いていること**とされた。OAuthを捨ててテンプレートURL／.icsを本命に格上げすれば、デモ画面は変わらないまま「動かないリスク」だけが消える。**そこで浮いた時間を値札の実装に充てる**のが、本案を通す場合の現実的な配分。

## 12. 今回作らないもの

- 記録（視聴履歴・スクリーンタイム）からの関心抽出 → 展開性に置く
- 資産形成の助言、投資商品の推奨（値札を出すまでで止める）
- 報酬設計（予約した額を確保できた月に何が起きるか）
- アカウント、クラウド保存、端末間同期

## 13. 要確認

v0.2の要確認3点（テイクアウトの中身・エクスポート所要時間・スクショ読み取り精度）は、記録の取り込みを取り下げたため**すべて不要になった**。

残る確認事項は、値札に使う統計の参照値をどこまで用意するか（B案の第13章と共通の論点）。
