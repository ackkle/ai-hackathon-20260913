- 作成日：2026年9月13日（v0.1）／更新：2026年9月13日（v0.2）
- 位置付け：個人案。チームの正式仕様ではない。
- v0.2での変更：v0.1の未決事項4点を決定。A案との関係と、統合会議で先に決めるべき論点を追記。

## 1. 一文で

自分で選んだわけではない空白が降ってくる人に、本人が意図せず残した記録から「実はもう興味を持っている未来」を見つけ、時間とお金の値札をつけて予約させるアプリ。

## 2. 背景・前提

- 10年後、稼ぐこと・働くことの多くをAIが代わりに行う
- 浮いた時間の使い方を、多くの人は決められない
- 週休3日制の導入企業では、この問題はすでに起きている

## 3. 審査観点との対応

| 観点 | 一言 |
|---|---|
| 価値 | 稼ぐことをAIがやる世界で、浮いた時間を何に使うか決められない人のためのもの |
| 実現性 | 手元にある記録（履歴・スクリーンタイム）だけを入力にするので今日動く。週休3日の会社ではすでに起きている問題 |
| 新規性 | 願望を聞かない。記録から本人が言葉にしていない未来を先に見せ、計画ではなく「予約」として時間とお金を確保させる |
| AIの活かし方 | 記録の集計結果 → 関心の抽出 → 10年後の具体的な生活と値札への翻訳。AI以外では成立しない |
| 展開性 | AIが労働を代替する速度に比例して対象者が増える。今は一部、10年後は全員 |

出力が「10年後の生活」そのものである点が、お題（10年後の当たり前）への直接の答えになる。

## 4. ターゲット

### 4.1 定義

外から空白が降ってくる人。やる気がないのではなく、やる気を仕事に吸われていて、空白を感じたことがない。だから空白が来ることが少し怖い。

| 空白の降り方 | 具体像 | 位置づけ |
|---|---|---|
| AIが仕事を減らす | 30代エンジニア | 主ペルソナ（デモ） |
| 会社が週休3日にする | 増えた1日の使い方が分からない会社員 | 実現性の根拠 |
| 定年が来る | 10年後の60代＝今の50代 | 展開性 |
| 就活が終わる | やることのない大学生 | 展開性 |

### 4.2 主ペルソナ

**亀野ながれ（35）**
都内在住。通信系企業でR&Dエンジニア。副業でAIによる管理規約書類の自動化を1人で回す。実家はやきとり屋。

- 副業の自動化が進み、1件の手作業は3時間→40分に。空いた時間は次の自動化とハッカソンに消える
- 週末はランニングとスマホ。YouTube履歴に「頼まれてもいないのに見ている動画」があるが、それを関心だと思っていない
- 先週、会社が週休3日制の試験導入を発表。増えた1日で何をするか思いつかなかった
- 10年後は45歳。副業も本業の一部もAIがやる。実家を継ぐか聞かれるが、答えはない

**アプリを開く瞬間**
発表の翌週、日曜の夜。YouTubeを1時間見たあと「自分は何を見ていたんだろう」と思ったとき。

**最初に刺さる一文**
「あなたは半年間で、◯◯の動画を◯本見ています。来年度から年間52日の空白が入ります。」

## 5. 提供価値

気づきではなく、**時間とお金を先に確保した未来が1つできること**。

## 6. 体験の流れ

1. **空白を見せる** — すでに年間◯時間の空白があると提示する
2. **関心を掘り出す** — 記録から、頼まれてもいないのに見ているものを抽出し「実は◯◯に興味がある」と突きつける
3. **値札をつける** — 「10年後にそれを週3日やるなら、初期費用◯円、月◯円、週◯時間」
4. **予約する** — 値札つきの予約票を発券し、最初の1日を確定する
5. **（A案を採用する場合）伴走する** — 実行結果と気持ちを記録し、次の予定を調整する

資産をどう作るかは本人の仕事。本案は値札を出すまでで止める。

## 7. 入力（v0.2で確定）

方針：**本人が意図せず残した記録**を使う。願望は聞かない。

| 種類 | 取り込み方 | 読み取るもの |
|---|---|---|
| YouTube視聴履歴 | Googleテイクアウトのzipをドラッグ&ドロップ | 関心 |
| スクリーンタイム | スクリーンショット1枚 | すでにある空白の量 |

### カレンダーを入力から外した理由

空白の量はカレンダーを読まなくても制度から計算できる（週休3日 → 年52日 → 10年で520日 → 可処分8時間換算で4,160時間）。OAuth連携の実装コストを払って得られる上積みは「土曜午後が3ヶ月連続で空いている」という粒度の細かさだけで、ハッカソンの持ち時間に見合わない。

代わりにスクリーンタイムを使うと「空白は未来の話ではなく、すでに起きている」という主張になる（例：週14時間スマホを見ている＝年間728時間）。体験の流れ①が強くなり、実装はスクショ1枚の読み取りで済む。

### 取り込みの設計

- zipはブラウザ内で展開し、チャンネル名を頻度集計する
- **LLMに送るのは集計結果の上位N件だけ。生の視聴履歴は送らない**
- サーバーに履歴を保存しない

トークン量の都合で必然的にこうなるが、副作用として「プライバシーは？」に即答できる。また「集計＝コード、意味づけ＝AI」の切り分けが明確になり、AIの活かし方の説明がしやすくなる。

## 8. 出力（v0.2で確定）

**値札つきの予約票1枚＋最初の1日の確定。**

| 券面項目 | 内容 |
|---|---|
| 予約番号 | 形式例。実装では重複を避ける |
| 10年後の生活 | 1行（例：週3日、◯◯をしている） |
| 根拠になった記録 | 抽出元の集計結果を明示する |
| 確保する空白 | 年◯日／年◯時間 |
| 値札 | 初期費用◯円／月◯円／週◯時間 |
| 最初の1日 | 日時と、その日にやること |

10年後の抽象と直近の具体を1画面に載せる。「予約」が「計画」と違うのは取り消しコストがあることなので、値札を券面に刷ることでそれを成立させる。

A案の予約票と器は同じ。**差分は「値札」と「根拠になった記録」の2項目**。

### 報酬設計を今回のスコープから外す

v0.1の未決事項「予約した額を確保できた月に何が起きるか」は解かずに落とす。継続利用の話なのでデモ1回では見えず、作り込むと却下したはずの資産形成コンサルに寄る。展開性の口頭説明に回す。

## 9. AIの役割

集計結果 → 関心 → 値札つき未来への翻訳、の1箇所に集中させる。

**本案はAIを使う箇所が1つしかないため、その出力品質がそのまま勝敗になる。** 素直に抽出すると「筋トレ」「キャンプ」「料理」のような凡庸な結果が出る確率が高い。刺さるのは「自分でも見ていると思っていなかったもの」で、効きそうな軸は、自分で検索して見たものと、流れてきたのに最後まで見たものの区別。前者は既に言語化された関心で、後者が「意図せず残した記録」の本体。

プロンプトの作り込みには他の実装より多く時間を割く。

オプション：賛成役ではなく反対役（「それでも予約しますか？」）。

## 10. A案との関係

A案は伴走ループの施工図（画面・データ・完成条件）、本案は入口と出口の企画。**層が違うので競合しない。**

v0.1の未決事項「予約の出力形式」は、A案の第5章が先に解いている（予約番号・始める言葉・気が重いときの代替行動）。

| 論点 | 採用する案 | 理由 |
|---|---|---|
| 入口 | C案 | A案の「明日を、どんな日にしたいですか？」は本人に願望を聞いている。本案の主張と正面からぶつかる |
| 値札・10年後の提示 | C案 | A案の到達点は「明日の楽しみ」で、10年後を前提条件にしか使っていない |
| 予約票の器 | A案 | すでに設計済み。C案は値札と根拠の2項目を足すだけ |
| 週間リスト・振り返り・承認付き予定調整 | A案 | 本案に設計がない |
| 保存・失敗時の動作・データ形式 | A案 | 本案に設計がない |

これは折衷ではなく、A案の機能①だけを差し替える構造の操作。INTEGRATION.mdの「全員の要素を均等に入れない」方針に沿う。

## 11. 統合会議で先に決めること

### 11.1 ペルソナ（これを決めないと他が決まらない）

A案の中心ペルソナは48歳事務職の佐藤さん、本案は35歳エンジニア。

**佐藤さんはGoogleテイクアウトでYouTube履歴を書き出せない。** 本案の入口は、エンジニアのペルソナだからこそ成立している。

| 決定 | 帰結 |
|---|---|
| ペルソナをA案に寄せる | 本案の入口が成立しない。新規性の土台が消える |
| ペルソナをC案に寄せる | A案のマインド面の設計（動けない日を責めない）がやや過剰装備になる |

先にここを決め、他の論点はその後に回す。

### 11.2 実装量の上限

A案の完成条件は20項目以上あり、4時間・3人にはおそらく多すぎる。そこへ本案の入口を足すと確実に溢れる。実現性は同点時の第1タイブレーカーなので、**削る順番を実装開始前に決めておく**。

本案を採用する場合の削り順（案）：反対役 → スクリーンタイム読み取り（固定値で代替）→ 伴走ループの振り返り以降。

## 12. 今回作らないもの

- 資産形成の助言（値札を出すまでで止める）
- 報酬設計
- カレンダー連携・認証
- 記録のサーバー保存、アカウント、端末間同期

## 13. 要確認（いずれも未検証）

実装前に公式ドキュメントで裏取りが必要。前提が崩れると第9章の設計が変わる。

- Googleテイクアウトの視聴履歴データに、検索経由かおすすめ経由かを判別できる情報が含まれるか。含まれない場合、第9章の軸を別の代理指標（視聴時刻帯、チャンネル登録の有無など）に置き換える必要がある
- テイクアウトのエクスポート完了までの所要時間。デモ当日に取得する運びにしない前提でも、事前準備のリードタイムとして把握が必要
- スクリーンタイムのスクリーンショットからの数値読み取り精度
