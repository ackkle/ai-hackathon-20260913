# リザーブマシン — 正式MVP仕様の提案版

作成日：2026年9月13日

**状態：AIによる提案・チーム未承認。実装開始の合意ではありません。**

計画の基準は「残り2時間30分」と回答された時点。実際の開始時に残り時間を更新する。3人でレビューし、決定を反映した `mvp-spec.md` を正式仕様とする。個人案は上書きしない。

## 1. 最初に確認してほしいこと

1. B案を軸に、下記の小さな体験へ絞る方針でよいか。
2. カレンダーは追加画面を開いて本人が保存する方式でよいか。
3. 利用可能なAI API・デプロイ先と、この担当分担で進められるか。

修正意見は「変更したい項目／理由／代わりに削るもの」の形で出す。3人全員の要素を入れることは目的にしない。

## 2. 目的と対象者

**仕事がなくても、明日が楽しみになる。曖昧な願いを、実行できる予定に変える。**

中心の対象者は、仕事中心に過ごしてきて、自由な時間が増えても何をしたいか分からない人。やりたいことがある人も同じ入口で受け入れる。

予定と実行結果が保存され、前回の結果を踏まえて次の一歩を提案する。これを単発の相談との体験上の違いとして見せる。

## 3. 採用方針と出典

**推奨：B案を主軸に、必要な要素だけ補強し、実装範囲を縮小する。**

| 判断 | 元の案・節 | 理由 |
| --- | --- | --- |
| 願い→質問→目指す状態→行動の流れを採用 | [B §3](member-b.md) | 抽象的な願いが予定になる変化を実演しやすい |
| 「まだ分からない」の選択肢と負担を軽くする支援を採用 | [A §3](member-a.md)、B §3 | 願望のない人も始められ、できなかった後の価値も示せる |
| 必要時間・費用の目安を行動カードに表示 | [C §6](member-c.md)、B §3 | 本人が実行できそうか判断できる。費用は推定と本人の予算を区別する |
| 予約・振り返り・次の一歩の保存を採用 | A §7、B §6 | 会話の外で継続する体験を作る |
| カレンダー追加リンク方式を提案 | B §6 | 認証連携を必須にせず、実際の予定へ渡す |
| 多階層の逆算ツリー、統計データ集、お金の逆算は見送り | B §3・9 | 調査・計算・再計算の実装より、一連の体験の完成を優先 |
| 記録の自動取り込み、年間空白、10年後の詳細費用予測は見送り | C §6〜10 | 入力方法と推定の検証が必要。準備済みデータがある場合はチームで再判断 |

全体の見立て：Aは外部依存が少なく継続支援が強い。Bは願いから予定への道筋を見せやすい。Cは潜在的な関心を発見する驚きが強いが、取り込み方法が未確定。Bの全機能をそのまま採用する提案ではない。環境・データの準備状況で判断は変わりうる。

## 4. MVPの操作

1. **入口**：願いを入力、または「まだ分からない」を選ぶ。
2. **質問3つ**：希望する過ごし方・使える時間・予算を選択。質問は固定し、動的な質問生成は省く。「分からない」も可。
3. **体験選択**：AIが体験候補を最大3つ生成。本人が1つ選ぶ。各候補に「目指す状態」「最初の行動」「所要時間」「費用目安」「準備」を付ける。
4. **予約**：最初の行動1件の日時を本人が設定し、予約票を保存する。カレンダー追加リンクを表示する。
5. **振り返り**：「できた／少しできた／できなかった」と、任意の気持ち・感想を記録する。
6. **次の一歩**：AIが直前の記録から次の行動を1件提案。本人が日時を決めて承認した場合だけ、新しい予約票にする。

休む・保留も選べる。外部施設の予約や決済、他人への連絡はしない。

## 5. 保存・AI・カレンダーの最小仕様

- 保存対象：願い、回答、選択した体験、現在の予約1件、過去の予約と振り返り。端末のブラウザに保存し、再読み込みで復元する。
- 初回生成と振り返り後の生成はサーバーからAI APIを呼び出す。キーをブラウザに置かない。サービスとモデルは未決定。
- AI出力の必須項目と件数を検証する。生成中は二重送信を防ぎ、失敗時は入力・振り返りを残して再試行する。
- 気持ちは「楽しかった／ふつう／しんどかった／回答しない」。任意で「またやりたい／別のことを試したい」を記録できる。
- 自由記述を含め、本人が書いていない感情を断定しない。進捗件数を幸福度や人の価値として表示しない。
- 時間・費用は本人の条件に合わせる。未確認の料金は目安と表示し、実在施設の空き状況を生成しない。
- 日時は日本時間。過去日時は確定できない。現在の予約は1件で、次を承認すると前の予約と結果を履歴に残す。
- 振り返り記録とAI提案を保存し、再試行で履歴を重複追加しない。AI提案だけで日時を変更しない。
- カレンダー追加リンクを開いただけでは、実際に保存されたと判断しない。アプリ内の「予定確定」と「カレンダー保存済み（本人確認）」を区別する。
- アプリからカレンダーへの更新・削除の自動同期はしない。登録後の変更はカレンダー側でも本人が行う旨を表示する。
- 記録の全削除ができる。新しい願いに変更するときは既存記録を置き換えることを確認する。

## 6. 完成条件

- 願い入力と「まだ分からない」の両方から予約票まで進める。
- 現在の予約と振り返りが再読み込み後も残る。
- 「できなかった・しんどかった」から、負担の小さい次の一歩を提案できる。
- 次の予約は本人の承認後にだけ保存され、過去の振り返りが残る。
- カレンダー追加画面に正しい件名・日時・説明が渡り、本人が保存できることをデモ用アカウントで確認する。
- 公開URLでスマホ幅でも一巡操作できる。AI失敗時に入力が消えない。
- 紹介動画と発表が実装済みの内容に一致し、提出できる。

## 7. 3人の分担案

| 担当 | 開発 | 公開・発表準備 |
| --- | --- | --- |
| A（あなた） | 予約票・日時・履歴保存・画面の接続 | デプロイ、動作確認、提出取りまとめ |
| B | 入口・質問・体験選択 | 企画判断、発表資料、登壇 |
| C | AI接続・生成指示・振り返りと次の提案 | 紹介動画の録画・編集 |

Bを企画の判断役にするのは会話で示された希望。実際の割り当ては3人で確認する。Aに負荷が偏ったら共通画面作業をBへ分ける。

ディレクトリ案（技術選定後に確定）：

```text
src/
  features/
    discovery/       # B：入口・質問・体験選択
    reservation/     # A：日時・予約票・履歴
    reflection/      # C：振り返り・次の提案
  server/ai/         # C：AI接続・指示文
  shared/types/      # 共通データ形式：最初に3人で確定
  shared/ui/         # 共通表示：変更時に共有
  app/               # 画面の接続：Aが取りまとめ
docs/presentation/   # B：発表
demo/                # C：サンプル・動画素材
```

共通データは「回答」「体験候補」「予約」「振り返り」に分けて型とサンプルを先に揃える。各自のブランチで作業し、小さなPull Requestをこまめに取り込む。

## 8. 150分の配分案

| 開始から | 到達する状態 |
| --- | --- |
| 0〜15分 | 方針・技術・データ形式を確定 |
| 15〜45分 | 仮画面を公開し、3人が並行実装 |
| 45〜90分 | AIと画面を接続、一巡を完成。機能追加を終了 |
| 90〜120分 | A：修正・公開確認、B：発表準備、C：動画制作 |
| 120〜150分 | リハーサル、提出、予備時間 |

遅れた場合は装飾と追加機能を先に削る。公開確認・録画・提出時間は残す。

## 9. デモの筋書き

「時間はある。でも何をしたいか分からない」→ 少し外に出たい・15分・予算0円 → 近所を歩いて写真を1枚撮る体験 → 日時を予約 → デモ用の実行結果として「できなかった・しんどかった」を記録 → 玄関の外で1枚撮る案 → 次の予定へ。

締めの言葉：**「仕事がなくても、明日が楽しみになる。できなかった日にも、次の一歩を一緒に作ります。」**
