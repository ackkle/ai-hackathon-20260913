# リザーブマシン MVP仕様書 — メンバーA案

- チーム：AIハッカソン・チーム15
- 作成日：2026年9月13日
- 位置付け：ユーザーとの対話をもとにした個人案。チームの正式仕様ではない。
- 想定：3人で開発するスマホ対応Webアプリ。技術構成と利用可能時間は統合時に決定する。

## 1. コンセプト

**やりたいことが見つからない人も、あるけど動けない人も、最初の一歩を予約できるリザーブマシン。**

「10年後、働く必要が減り、自由な時間が増えたら」という未来を想定する。願望を受け取って具体的な行動と予定に変え、実現に向けて支援する。

長期的には趣味・上達・暮らし・お金など幅広い願望に伴走する。今回のMVPは、趣味を中心に「最初の1週間の行動を提案し、その中の最初の1件を本人が予約する」体験に絞る。

## 2. 対象者と解決する課題

| 対象者 | 困りごと | 利用後の状態 |
| --- | --- | --- |
| やりたいことがある人 | 何から始めるか、どう上達するか分からない | 自分に合った最初の行動と日時が決まる |
| やりたいことを探している人 | 興味はあるが趣味を選べない | 試す趣味を1つ選び、最初の行動と日時が決まる |

完成時に提供する価値は「願いの実現を保証すること」ではなく、「自分で納得して選んだ行動を予定にすること」。

## 3. MVPの主要機能（3つ）

### ① 願望の入力・発見

最初に「やりたいことがある」「やりたいことを見つけたい」の2つから選ぶ。

- ある人：願望を自由入力し、経験・使える時間・予算を回答する。
- 探す人：気になること・使える時間・予算を回答する。AIが趣味を3つ提案し、本人が1つ選ぶ。経験は未経験を初期値として変更できる。
- 回答は選択肢を中心にし、自由記述を補助として使う。「分からない」「特にない」も選べる。
- 趣味の候補は、名前・合いそうな理由・最初に試すことを表示する。
- 候補が合わなければ条件を編集して再提案できる。

### ② 最初の1週間の行動を具体化

- AIが、本人の条件に合う「目指す状態」と、今後7日間で試す行動を最大3件提案する。
- 各行動に、内容・所要時間・必要な準備を付ける。
- 初心者がいきなり成果を出すことを前提にせず、探す・試す・振り返るなど実行できる粒度にする。
- 「目指す状態」と「自分がやりたい理由」は本人が編集できる。AIの推測を本人の回答として扱わない。

### ③ 最初の行動を予約・発券

- 本人が行動を1件選び、日時を設定して「この一歩を予約する」を押す。
- 確定後に予約番号付きの予約票を表示し、この端末のブラウザに保存する。
- 「予約」は本人の行動予定の確定を意味する。店舗・教室・相手への予約や連絡は行わない。
- 1週間の行動案は表示するが、MVPで発券・保存するのは最初の1件のみ。

## 4. 画面と操作の流れ

| 画面 | 表示・入力する内容 | 主な操作 |
| --- | --- | --- |
| 入口 | コンセプトと2つの入口 | ある／見つけたいを選ぶ |
| 条件入力 | 願望または興味、時間、予算、必要に応じて経験 | 提案を作る |
| 趣味候補（探す人のみ） | 3候補とその理由 | 1つ選ぶ／条件を直す |
| 行動案 | 目指す状態、やりたい理由、最大3件の行動 | 内容を調整し、1件と日時を選ぶ |
| 予約票 | 確定内容、予約番号、始めるための言葉 | 予定を編集／新しく作る |

共通の流れ：願望 → 簡単な質問 → 行動案 → 本人が日時を決定 → 予約票。

## 5. 予約票の内容とマインド面の支援

| 項目 | 表示例 |
| --- | --- |
| 予約番号 | RM-20260913-001（形式例。実装では重複を避ける） |
| やりたいこと | テニスでラリーを楽しみたい |
| 自分の理由 | 休日に体を動かす仲間がほしい |
| 今回の一歩 | 初心者向け体験教室を1件探す |
| 日時・所要時間 | 2026年9月16日 20:00〜20:15・15分 |
| 場所 | 自宅 |
| 準備 | 参加できる日程と予算を確認する |
| 気が重いときは | 教室のページを1つ開くだけでもOK |
| 始める言葉 | 今日は、始める場所が1つ見つかれば十分です。 |

マインド面は独立したチャット機能にせず、「自分の理由」「行動を小さくする代替案」「短い言葉」に組み込む。未実行を責める表現や成功の断言はしない。

## 6. AIと本人の役割

| AIが提案すること | 本人が決めること |
| --- | --- |
| 趣味の候補と理由 | 何を試したいか |
| 現状に合った目標の案 | 目指したい状態・自分の理由 |
| 最大3件の行動と準備 | 実行する行動・日時・予約の確定 |
| 小さな代替行動と始める言葉 | 提案を採用するか、変更するか |

生成時の共通ルール：

- 回答された時間・予算・経験に合わせる。不明な情報は確定情報として扱わない。
- 実在施設の空き状況・料金・他人の参加承諾を作り上げない。未確認の場所は候補として扱う。
- 「お金持ちになりたい」など広い願望には、目的を具体化し、学習や現状整理などの最初の行動を提案する。利益や達成を保証しない。
- スポーツでは経験に合う小さな一歩を提案し、個別の診断や無理な運動指示を行わない。
- 実現が難しい願いも一方的に否定せず、背景にある希望に近い体験を候補として提示する。

## 7. MVPの実装方針（統合時に技術選定）

- スマホとPCで使うWebアプリ。ログインは不要。
- AIの呼び出しはサーバー側で行い、APIキーをブラウザに渡さない。
- 趣味候補と行動案は構造化データで受け取り、アプリ側で必須項目・件数を検証する。
- 生成中は処理中の表示を出し、二重送信を防ぐ。
- 生成失敗や形式不正では入力を保持し、再試行できる。成功したような予約票は表示しない。
- 日時は日本時間。相対表現は実際の日付にし、確定前に表示する。過去日時は確定できない。
- 予約票は最新1件をブラウザのローカル保存領域に保存し、再読み込みで復元する。端末間同期はしない。
- 新しく作るときは、現在の予約票を置き換えることが分かる表示にする。
- 保存に失敗した場合はその旨を表示し、画面上の予約票は残す。

最低限のデータ：入口の種類、願望／興味、経験、時間、予算、選んだ趣味、目標、本人の理由、行動案、選んだ行動、開始日時、所要時間、準備、場所、代替行動、始める言葉、予約番号。

## 8. 今回は作らないもの

- 長期の成長管理、実行履歴、習慣化の分析
- 予定の自動組み直し、通知、継続チャット
- 店舗・教室の実予約、決済、他人への招待
- Googleカレンダーとの認証・同期
- アカウント、クラウド保存、端末間同期

余裕があれば、予約票のカレンダーファイル（.ics）出力を追加する。必須機能の完成を優先する。

## 9. 完成条件

- 「ある」入口から、入力→行動案→日時選択→予約票まで進める。
- 「見つけたい」入口から、3つの趣味候補→選択→行動案→予約票まで進める。
- 行動案は最大3件で、本人が選んだ1件と日時が予約票に正しく反映される。
- 予約票に準備・小さな代替行動・始める言葉が表示される。
- 空欄の願望や未選択の趣味では先に進めず、過去日時を確定できない。
- AIのエラー時に入力が消えず、再試行できる。
- 再読み込み後に最新の予約票が復元される。
- スマホ幅で入力から発券まで操作できる。
- 実際に行っていない手配を「予約済み」と表示しない。

## 10. デモ例

### A：やりたいことがある

「テニスが上手くなりたい」→ 未経験・週末1時間・予算3,000円 → 初心者向けの最初の行動 → 教室を探す日時を本人が決定 → 予約票。

### B：趣味が見つからない

「静かな時間が好き」・週30分・予算1,000円 → AIが3候補 → 本人がスケッチを選択 → 家にある紙と鉛筆で5分描く予定 → 予約票。

候補や文面は例であり、実際のAI出力と一致する必要はない。条件に合った行動へ進めることを確認する。

発表の一言：**「漠然とした願いが、その場で予定に変わります。」**

## 11. 3人の担当案と進め方

| 担当 | 主に作る範囲 |
| --- | --- |
| A | 入口・条件入力・趣味候補の画面 |
| B | AIへの指示文、サーバー処理、出力の検証 |
| C | 行動案の調整・日時選択・予約票・ローカル保存 |

開発前に3人で画面間のデータ形式を固定する。最初は固定サンプルデータで画面をつなぎ、その後AI処理に置き換える。動作確認と発表準備は全員で行う。

4時間の場合の配分例：仕様統合・技術決定30分、画面とAI処理の並行開発90分、接続と修正60分、通し確認と発表練習60分。

## 12. 統合時にチームで決めること

これは本案の不足を埋めるためではなく、3案から正式仕様を選ぶための判断事項。

- 中心にする利用者・デモの題材
- 2つの入口を両方実装するか
- 1週間の提案と最初の1件の発券という範囲
- ローカル保存を必須にするか、発券までにさらに絞るか
- 使用技術、AIサービス、実際の残り時間、各自の担当
