- 作成日：2026年9月13日

## 1. コンセプト

**曖昧な願いを、今日の予定に変える。**

リザーブマシンは、「お金持ちになりたい」「なんか、このままじゃまずい気がする」のような、まだ形になっていない願いを受け取り、本人への質問と統計データをもとに、目指す状態・必要な数字・今週の行動まで逆算し、Googleカレンダーに予定として入れるアプリ。予定が完了すると次の一歩が再計算される。

想定する未来は「10年後、AIが仕事の多くを担い、人の自由な時間が増えた世界」。仕事が与えてくれていた予定・役割・目標がなくなっても、人が自分の「やりたい」を失わず、曖昧な願いのまま止まらずに動き出せることを、10年後のあたりまえにする。

機能の判断基準は **「この人の曖昧な願いが、今日の予定になったか」**。行動量や達成度で人の価値を測らない。「不要」「堕落」といった人を評価する表現は、画面・AI出力・発表のすべてで使わない。休む選択も予定として尊重する。

### 一般的なAIチャットとの違いとして実装する価値

| 違い | 内容 |
| --- | --- |
| 聞かれる前に聞く | 本人が自分では答えを持っていない前提（望む生活の月額、使える時間、許容できる負担）をAIが先に質問して埋める。一問一答の壁打ちでは本人が質問を思いつく必要がある。 |
| 主観を数字に変える | 「ゆとりのある生活」「人に見せられる何か」を、公的統計と本人の回答から具体的な数字・状態に翻訳し、出どころを画面に表示する。 |
| 予定が外に出て、結果が戻る | 逆算した行動がGoogleカレンダーに登録され、完了の記録が逆算ツリーに戻って次の一歩が再計算される。会話の中で完結しない。 |

特定のAI製品で同じことが不可能だとは主張しない。比較対象は単発の会話体験。

## 2. 対象者と解決する課題

### 中心ペルソナ：AIに仕事を減らされて、時間はあるが「やりたい」がない人

けんたさん、32歳（架空の人物・仮設定）。年齢や性別より「仕事が減って時間が増えたのに、何をしたいか分からない」状況を重視する。

| 項目 | 設定 |
| --- | --- |
| これまで | 事務職。資料作成と集計はAIが担うようになり、残業がほぼゼロに |
| 生活 | 平日は19時に帰宅してSNSと動画で就寝。休日はスマホ使用7時間、予定なし |
| 変化 | 時間はできたが、仕事以外に目標も趣味もない |
| 本音 | 「なんか、このままじゃまずい気がする。何かしたい。でも何を？」 |
| 始められない理由 | 願いが曖昧すぎて、最初の一歩が決められない。決めても予定にならず流れる |
| 欲しい変化 | 曖昧なままの願いを言葉にしたら、今週やることがカレンダーに入っている |

同じ仕組みで「お金持ちになりたい」「英語を話せるようになりたい」のような願いも扱う。対象者は絞り、願いの幅で展開する。

### 利用前後の変化

| 利用前 | 利用後 |
| --- | --- |
| 願いが曖昧で、何から始めるか分からない | 願いが「目指す状態→数字→今週の行動」の木に分解されている |
| 決めたことが予定にならず流れる | 行動がGoogleカレンダーに日時つきで入っている |
| やったかどうかが残らない | 完了・未完了が記録され、次の一歩が再計算される |

利用後の状態は「今週の予定が1件以上カレンダーに入り、完了で次が出る」こと。願いの実現や達成速度は保証しない。

## 3. MVPの主要機能（4つ）

### ① 願いのインタビュー

- 願いを自由入力する。「お金持ちになりたい」「何かしたい」のように曖昧でよい。「まだ分からない」も入力できる。
- AIが、逆算に必要で本人が答えられる質問を最大5問返す。例：望む生活の月額、使える時間（平日・休日）、現在の貯金、許容できる負担（体力・費用・人と会うか）。
- 回答は選択肢を中心にし、「分からない」を選べる。分からない項目はAIが統計の中央値などで仮置きし、「仮」と明示する。
- 質問は願いの種類で変わる。お金の願いなら資産・支出、趣味や活動の願いなら時間・体力・費用。

### ② 逆算ツリーと数値化

- AIが「願い → 目指す状態（1年後・3年後） → 必要な数字 → 月の行動 → 今週の行動（最大3件）」の木を生成する。
- 数字には出どころを付ける。本人の回答か、統計の参照値か、AIの推定かを区別して表示する。
- 参照する統計は事前にアプリに持たせる（例：家計調査の単身世帯の支出、年齢別の貯蓄分布、余暇時間の平均、活動別の費用相場）。AIは参照値を根拠として引用し、AIの推定を統計として表示しない。
- 目指す状態と数字は本人が編集できる。編集すると下の階層が再計算される。
- 願いが広い場合は、目的の具体化そのものを最初の行動にする（例：「お金持ち」→「望む生活の月額を1つ決める」）。利益や達成は保証しない。投資商品の推奨は行わない。

### ③ 今週の行動をGoogleカレンダーに登録

- 今週の行動（最大3件）に、内容・所要時間・準備・気が重いときの小さな代替案を付ける。
- 本人が使える曜日・時間帯から、AIが日時候補を出し、本人が確定する。
- 確定した行動をGoogleカレンダーに予定として登録する。予定の説明欄に「願い」「今回の一歩」「準備」「代替案」を書き込み、カレンダー側だけを見ても動けるようにする。
- 登録済みの予定にはカレンダーのリンクを表示する。
- 「予約」は本人の行動予定の確定を意味する。店舗・教室・相手への予約や連絡は行わない。

### ④ 完了チェックと再計算

- 行動ごとに「できた／少しできた／できなかった」と、任意で「楽しかった／ふつう／しんどかった」を記録する。
- 記録すると逆算ツリーの進捗が更新され、AIが次の一歩を1件提案する。できた場合は次の段へ、できなかった場合は負担を小さくする案や休む案を出す。
- 本人が承認した場合だけ、次の行動をカレンダーに登録する。
- 時刻を過ぎた予定は「確認待ち」とし、自動で失敗扱いにしない。

## 4. 画面と操作の流れ

| 画面 | 表示・入力する内容 | 主な操作 |
| --- | --- | --- |
| 入口 | コンセプトと願いの入力欄 | 願いを書く／「まだ分からない」を選ぶ |
| 質問 | 最大5問。選択肢中心、「分からない」あり | 回答して逆算を作る |
| 逆算ツリー | 願い→目指す状態→数字（出どころつき）→月の行動→今週の行動 | 数字や状態を編集して再計算 |
| 日時決定 | 今週の行動最大3件と日時候補 | 日時を確定してカレンダーに登録 |
| ホーム | 次の予定、今週の行動、ツリーの進捗、カレンダーのリンク | 完了を記録／ツリーを開く |
| 完了記録 | 実行結果、任意の気持ち、AIの次の一歩 | 記録／次の一歩を承認または保留 |

共通の流れ：願い → 質問 → 逆算ツリー → 日時決定 → カレンダー登録 → 完了記録 → 再計算。再訪時は保存されたホームを開く。

## 5. AIと本人の役割

| AIが提案すること | 本人が決めること |
| --- | --- |
| 逆算に必要な質問 | 答えるか、「分からない」にするか |
| 目指す状態・数字・出どころ | 目指す状態と数字の最終値 |
| 今週の行動最大3件と日時候補 | 実行する行動と日時、カレンダー登録の確定 |
| 完了記録を踏まえた次の一歩 | 採用・変更・保留 |

生成時の共通ルール：

- 回答された時間・費用・体力に合わせる。不明な項目は「仮」と明示し、確定情報として扱わない。
- 統計の参照値と、AIの推定を区別して表示する。出どころのない数字を断定しない。
- 行動量や継続を人の価値に結びつけない。休む・別のことを試す選択を尊重する。
- 実在施設の空き状況・料金・他人の参加承諾を作り上げない。
- お金の願いは計画の整理を支援する範囲にとどめ、投資助言・商品推奨・利益の保証をしない。
- 願いが実現困難でも一方的に否定せず、背景にある希望に近い状態を候補として提示する。

## 6. MVPの実装方針（統合時に技術選定）

- スマホとPCで使うWebアプリ。
- AIの呼び出しはサーバー側で行い、APIキーをブラウザに渡さない。
- 質問・逆算ツリー・次の一歩は構造化データで受け取り、アプリ側で必須項目・件数・日時・数字の出どころを検証する。
- 統計の参照値はアプリ内の固定データ（JSONなど）として持ち、AIには参照値を渡して引用させる。
- Googleカレンダー登録は2段構え。
  - 本命：Google OAuth認証を通し、Calendar APIで予定を作成する。
  - 代替：認証が時間内に間に合わない場合は、予定の内容を埋め込んだGoogleカレンダーの「予定を追加」リンク（テンプレートURL）を開き、本人が保存する。`.ics` ファイルの出力も可。どちらの経路でも画面上は「カレンダーに入った」を確認してから登録済みにする。
- 生成中は処理中の表示を出し、二重送信を防ぐ。生成失敗や形式不正では入力を保持し、再試行できる。
- 日時は日本時間。相対表現は実際の日付にし、確定前に表示する。過去日時は確定できない。
- 願い・回答・逆算ツリー・今週の行動・完了記録・変更履歴をブラウザのローカル保存領域に保存し、再読み込みで復元する。端末間同期はしない。
- 完了記録を先に保存してからAIに次の一歩を求める。AIが失敗しても記録は残る。
- 行動は安定したIDで管理する。状態は「未登録／登録済み／できた／少しできた／できなかった／見送り」。

最低限のデータ：願い、質問と回答（分からない・仮置きの区別）、逆算ツリー（各ノードの内容・数字・出どころ）、今週の行動のID・状態・日時・所要時間・準備・代替案・カレンダー上のID、完了記録・気持ち（任意）・記録日時、変更前後の予定と承認日時。

## 7. 今回は作らないもの（展開性に置く）

- 位置情報・スマホ使用時間・アプリ利用状況による完了の自動判定
- 複数利用者の記録を集めた最短ルートの推薦
- 複数の願いの同時管理、長期の分析、通知、継続チャット
- 店舗・教室の実予約、決済、他人への招待
- アカウント、クラウド保存、端末間同期

## 8. 完成条件

- 曖昧な願い（「お金持ちになりたい」「何かしたい」）から、質問→逆算ツリー→今週の行動まで進める。
- 逆算ツリーの数字に出どころ（本人の回答／統計／AIの推定）が表示される。
- 目指す状態または数字を編集すると、下の階層が再計算される。
- 今週の行動は最大3件で、本人が確定した日時がGoogleカレンダーに登録され、アプリからリンクで開ける。
- OAuthが使えない環境でも、テンプレートURLか `.ics` でカレンダーに入れられる。
- 完了記録が逆算ツリーの進捗に反映され、次の一歩が1件提案される。
- 「できなかった」の記録から、負担を小さくする案か休む案が出る。
- 次の一歩は承認前にカレンダーを変更せず、承認後にのみ登録される。
- AIのエラー時に入力が消えず、再試行できる。
- 再読み込み後に願い・ツリー・予定・記録が復元される。
- スマホ幅で入口から完了記録まで操作できる。
- 実際に登録していない予定を「登録済み」と表示しない。

## 9. デモ例

### A：中心ペルソナ（発表の入口）

けんたさん、32歳。願いに「なんか、このままじゃまずい気がする。何かしたい」と入力 → 質問「休日に使える時間」「人と会うのは平気か」「使える費用」「体を動かすのは好きか」に回答 → 逆算ツリー「1年後に人に見せられる何かを持つ → 月2回、外で人と会う活動 → 今週：土曜10:00に地元の陶芸体験を予約する」 → Googleカレンダーに登録 → 土曜に「できた・楽しかった」を記録 → 次の一歩「2回目を来週に入れる」が提案される。

### B：お金の願い（逆算と数字の出どころ）

「お金持ちになりたい」→ 質問「望む生活の月額」「現在の貯金」「毎月の手取り」→ 逆算ツリー「45歳で年間支出の25年分（本人の月額×12×25）→ 月3.8万円の積立と固定費1.2万円の削減 → 今週：格安SIMの見積もりを取る（土曜10:00）」。数字の横に「本人の回答」「家計調査の参照値」「AIの推定」が表示される。投資商品は勧めない。

### C：できなかった後も続く（発表の中心）

「土曜10:00 陶芸体験を予約する」に「できなかった・しんどかった」を記録 → AIが「陶芸教室のサイトを5分だけ見る」を提案 → 本人が翌日の空き時間を選んで承認 → カレンダーに登録される。休む選択もでき、記録が残る。

候補や文面は例であり、実際のAI出力と一致する必要はない。

発表の一言：**「曖昧な願いを、今日の予定に変える。10年後、AIが仕事を担う世界で、『やりたいことがある人』をふつうにする。」**

## 10. 展開性（この先の3段階と10年後）

| 段階 | 内容 | 前提 |
| --- | --- | --- |
| 第1段階（今回） | 願いの逆算・数値化・カレンダー登録・手動の完了記録 | 統計の参照値とAI |
| 第2段階 | 本人がオンにした範囲で、位置情報やスマホ使用時間から完了を自動判定する。判定は端末内で行う | 端末OSが提供する利用状況APIなど、既に存在する仕組みを使う |
| 第3段階 | 匿名化した「出発点→行動→達成度」の記録を集め、似た出発点の人がたどった経路から最短ルートを提案する | 利用者の同意と、達成度の定義（行動列と本人の記録） |
| 10年後 | 願いを口にすれば、端末が行動を組み、記録し、整えてくれる。人は「やりたい」を持ち続けることに集中できる | 上の3段階の延長。脳や身体と直接つながる技術の進展は補助的な追い風として扱い、前提にはしない |

利用者が増えないと価値が出ない構造にはしない。第1段階は統計とAIだけで動き、第3段階の記録は第1段階の利用で自然に溜まる。

行動データの扱いは「本人がオンにした範囲だけ・端末内で判定・目的外に使わない」の3点を固定する。

## 11. 審査観点との対応

| 観点 | 提出物で示すもの |
| --- | --- |
| 価値（誰の役に立つか） | けんたさんの利用前後。曖昧な願いが今週の予定になる |
| 実現性（動くか） | 逆算ツリー・Googleカレンダーに入った予定・完了で再計算される画面の3つ |
| 新規性 | 一般的なAIチャットとの違い3点（聞かれる前に聞く／主観を数字に／予定が外に出て結果が戻る） |
| AIの活かし方 | インタビュー・逆算・数値化・次の一歩の4役を、統計の参照とセットで説明する |
| 展開性 | 第1〜3段階と10年後。コールドスタートの答えとプライバシーの3点 |

同点時は「動くか→誰の役に立つか」の順で比べられるため、カレンダー登録が実際に動く画面を最優先で用意する。

## 12. A案との共通点・違い（統合の材料）

| 論点 | 共通点 | B案の違い |
| --- | --- | --- |
| ミッション | 10年後、仕事が減っても「やりたい」を失わない。人の価値を行動量で測らない | 願いが曖昧なまま止まっている状態を入口にし、逆算と数字で動き出させる |
| 入口 | 願いがある人も、ない人も受け入れる | 2つの入口を分けず、1つの入力欄と質問で吸収する |
| 計画の範囲 | 1週間・最大3行動 | 上に「目指す状態」と「数字」の階層を持ち、編集で再計算する |
| 外部連携 | A案は後回し | Googleカレンダー登録を中心価値に置く。OAuthが間に合わない場合の代替経路を用意する |
| 振り返り | できた・気持ちの記録と次の一歩 | 記録が逆算ツリーの進捗に戻る |
| 展開性 | 幅広い願望への伴走 | 端末データによる自動判定と、匿名記録からの最短ルート推薦を段階で明示 |

## 13. 統合時にチームで決めること

- 「曖昧な願いを今日の予定に変える」を中心価値にするか、A案の「明日が楽しみになる」を中心にするか
- 逆算ツリーの階層（目指す状態・数字）をMVPに含めるか、行動3件だけにするか
- Googleカレンダー登録をMVPに含めるか。含める場合、OAuthか代替経路のどちらを本命にするか
- 統計の参照値をどこまで持つか（お金・時間・費用相場のどれを入れるか）
- 中心ペルソナ（A案の佐藤さん48歳／B案のけんたさん32歳）の統一
- 使用技術、AIサービス、実際の残り時間、各自の担当、デプロイ先
